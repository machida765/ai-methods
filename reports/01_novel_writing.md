## 3分で分かる要約

1. **AIは「代筆者」より「編集者・資料係・壁打ち相手」として使うと効率も品質も上がる。** 構想の発散、プロットの矛盾チェック、設定資料の整理、推敲の指摘、誤字脱字チェックはAIが得意。一方で「その作品らしい声」「読者を刺す一文」は人間が握るほうが結果がよい。
2. **ツールは三層で考える。** ①汎用チャットAI（Claude / ChatGPT / Gemini）＝思考・分析・長文読解、②小説特化ツール（Sudowrite / Novelcrafter / NovelAI / AIのべりすと）＝続き書き・文体模倣・設定管理、③エージェント型環境（Claude Code / Cursor＋MCP＋Agent Skills）＝設定資料をリポジトリ化して「作品全体を把握したAI」を作る。
3. **長編で効くのは「設定資料のリポジトリ化」。** キャラシート、世界観、プロット、章ごとの要約、文体ガイドをMarkdownファイルで管理し、`CLAUDE.md` やCursorのルールで「必ず参照せよ」と指示する。これだけで矛盾・キャラ崩壊が大きく減る。
4. **ワークフローは「構想→プロット→執筆→推敲→校正→投稿」の6段階。** 各段階で「AIに何をさせ、人間が何を決めるか」を分けておく。プロンプトは本レポートに40本以上掲載。
5. **規約は2026年に大きく動いた。** カクヨムは2026年5月27日にガイドラインを更新し「AI本文利用／AI本文一部利用／AI補助利用」タグを推奨（コンテストでは必須）。小説家になろうは2026年6月9日からAI利用状況の設定を必須化し、9月1日以降は未設定作品の更新が制限される。電撃小説大賞・MF文庫J新人賞などは「補助的利用のみ・申告必須・記録保存」。日経「星新一賞」はAI利用作品も受付（制作過程の記載が必要）。
6. **著作権の基本線**（文化庁「AIと著作権に関する考え方について」）: AIが自律的に生成したものは著作物にならない。人の「創作意図」と「創作的寄与」（詳細な指示、選択、加筆修正の積み重ね）があれば著作物になり得る。既存作品との類似性・依拠性があれば侵害になり得る。
7. **最大の落とし穴は「AIっぽい均質な文章」「設定の静かな崩壊」「規約違反の申告漏れ」「記録を残していないこと」。** プロンプトと生成物、修正履歴を残す習慣（Gitが最適）を最初から作る。
8. **今日から試すなら**: ①作品フォルダを作り `characters/` `world/` `plot/` `chapters/` を置く、②`CLAUDE.md` に文体と禁止事項を書く、③1章だけ「AIに批評させ→自分で直す」を回す。章末のチェックリスト参照。

## 第1章 前提: 2026年のAI小説執筆の現在地

### 1-1. 何が変わったのか

2023年ごろまでの「AI小説」は、短い続きを書かせて面白がる、あるいはアイデアを10個出させる、という使い方が中心でした。2026年現在は状況が大きく違います。主な変化は次の4つです。

| 変化 | 内容 | 小説執筆への影響 |
| --- | --- | --- |
| 長文コンテキスト | 主要な汎用モデルは数十万トークン級の入力を扱える（具体的な上限はモデル・プランで異なり要確認） | 長編1冊分の原稿や設定資料を丸ごと読ませて矛盾チェックができる |
| エージェント化 | Claude Code、Cursor、Codex CLIなど、ファイルを読んで書き換えるAIが一般化 | 「設定資料フォルダ」をAIが自分で参照しながら作業できる |
| MCPとAgent Skills | 外部ツール接続の標準（MCP）と、手順書パッケージ（SKILL.md形式のAgent Skills）が普及 | Notion・Obsidianの設定資料と接続、推敲手順を「スキル」として再利用 |
| 規約の整備 | カクヨム・なろうがAI利用の表示を制度化、新人賞が申告・記録保存を要求 | 「どこまでAIを使ったか」を記録・申告する運用が必須に |

### 1-2. 「AIに書かせる」と「AIと書く」の違い

効率化の観点で最も重要なのは、**AIに何を任せるかの線引き**です。経験的に、次のような分担が品質と速度のバランスがよいとされます。

- **AIが得意で任せてよい領域**
  - 発散: アイデア出し、タイトル案、キャラクター名候補、設定の「もしも」展開
  - 整理: 散らかったメモの構造化、時系列表の作成、キャラ相関図のテキスト化
  - 検査: 矛盾チェック、視点ブレ検出、誤字脱字、表記揺れ、冗長表現の指摘
  - 調査の入口: 時代考証や専門知識の「調べるべき論点」の洗い出し（事実確認は人間が一次資料で）
  - 批評: 読者視点での感想、離脱しそうな箇所の指摘、ジャンル慣習との比較
- **人間が握るべき領域**
  - その作品が「何を書きたいのか」というテーマと感情の核
  - 文体・語り口の最終決定（AIは平均的な文体に寄りやすい）
  - 決め台詞、山場の一文、ラストシーン
  - 規約・権利・倫理の判断
- **グレーゾーン（使い方次第）**
  - 下書き生成: 「骨組みだけAIに書かせ、人間が全面的に書き直す」は効率的だが、新人賞によっては禁止。なろうでは「AI間接利用」に該当し得る
  - 文体模写: 自分の過去作を見本にした「自分の文体の再現」は有効だが、他人の作品を大量に読ませての模倣は権利上のリスクがある

### 1-3. 効率化の本当のボトルネック

小説執筆で時間を食うのは、実は「本文を打つ時間」よりも次のような作業です。

1. 「次に何を書くか」が決まらず手が止まる時間
2. 過去の章を読み返して設定を確認する時間
3. 書き上げた後に矛盾や説明不足に気づいて書き直す時間
4. 推敲・校正で同じ観点を何度もチェックする時間

AIを入れて最も時間が減るのは2〜4です。つまり、**本文生成よりも「設定の外部記憶」と「検査の自動化」にAIを投資する**のが、規約上も品質上も安全で効果の大きい戦略です。本レポートの第3章（環境構築）と第4章（ワークフロー）はこの考え方に沿って組み立てています。

### 1-4. 本レポートでの用語

| 用語 | 意味 |
| --- | --- |
| 汎用チャットAI | Claude、ChatGPT、Geminiなどの対話型AIサービス |
| 小説特化ツール | Sudowrite、Novelcrafter、NovelAI、AIのべりすと等 |
| エージェント | ファイルの読み書きやコマンド実行を自律的に行うAI（Claude Code、Cursorのエージェント機能など） |
| MCP | Model Context Protocol。AIと外部ツール・データをつなぐ標準プロトコル |
| Agent Skills | `SKILL.md` を中心とした手順・知識のパッケージ。Claude Skillsとも呼ばれ、他のエージェントでも使える形式 |
| 設定資料リポジトリ | 作品の設定・プロット・原稿をフォルダ／Gitで管理したもの |
| コンテキスト | AIが一度に参照できる入力情報の全体 |

## 第2章 使えるAIツール/サービスの特徴と使い分け

### 2-1. 全体マップ

| 分類 | ツール | 強み | 弱み・注意 | 向いている工程 |

| 汎用チャット | ChatGPT（OpenAI） | 汎用性、プロジェクト／メモリ機能、画像生成との連携、カスタムGPT | 文体が「ChatGPTっぽく」均質化しやすい（プロンプトで調整） | アイデア発散、資料整理、挿絵・表紙の検討 |
| 汎用チャット | Gemini（Google） | 非常に長いコンテキスト、Googleドキュメント／ドライブ連携、検索との統合 | 出力の癖はモデル更新で変化（要確認） | 長編原稿の通読チェック、資料調査の入口 |

| エージェント | Claude Code | ファイル操作、CLAUDE.md、Skills、MCP、サブエージェント | ターミナル操作に慣れが必要（IDE拡張やデスクトップ版もある） | 設定資料リポジトリの運用、一括チェック |

| ノート | Obsidian / Notion | 設定資料の管理、リンク、データベース | AI機能は別途プラグインやMCP接続で補う | 設定資料の母艦 |

### 2-2. 汎用チャットAI

#### Claude

- **特徴**: 長い原稿を読ませた上での批評、文体の微調整、「この台詞はキャラらしいか」といった細かい判断が得意と評価されることが多いモデル群です。プロジェクト機能（Projects）に設定資料をアップロードしておけば、毎回説明し直す手間が減ります。
- **執筆での使いどころ**:
  - 原稿全体を読ませての矛盾チェック・伏線回収チェック
  - 「辛口編集者」役での批評
  - Claude Code と組み合わせた設定資料リポジトリ運用（第3章）
  - Agent Skills（SKILL.md）で「推敲手順」「校正ルール」をパッケージ化
- **注意**: 最新モデル名・コンテキスト長・料金プランは更新が速いため要確認。成人向け表現は利用ポリシーの範囲内で。

#### ChatGPT

- **特徴**: 利用者数が最も多く、情報も多い汎用AI。プロジェクト、メモリ、カスタムGPT、画像生成、音声会話など周辺機能が豊富です。
- **執筆での使いどころ**:
  - 散歩中の音声会話でのアイデア出し
  - カスタムGPTに「自作品専用の設定係」を作る
  - 表紙・挿絵のラフ検討（商用利用・投稿サイト規約は別途確認）
- **注意**: 何も指定しないと「〜のだった。」「静寂が支配していた」のような定型表現や過剰な比喩が出やすい傾向があります。文体ガイドと禁止表現リストを与えるのが有効です。

#### Gemini

- **特徴**: 長大なコンテキストと、Googleドキュメント／ドライブとの連携が強み。Googleドキュメントで書いている人には導入の摩擦が小さいツールです。
- **執筆での使いどころ**:
  - 長編原稿（数十万字）を一括で読ませての「登場人物の呼称一覧」「時系列表」の自動作成
  - 資料調査の入口（ただし出典は自分で一次資料を確認）
- **注意**: 機能名・プラン構成は頻繁に変わるため要確認。

#### 汎用チャットAIの使い分け早見表

| やりたいこと | 第一候補 | 理由 |
| --- | --- | --- |
| 原稿の辛口批評 | Claude | ニュアンスを捉えた指摘が得意とされる |
| 雑多なアイデア出し | ChatGPT / Claude | どちらも十分。音声ならChatGPTが手軽 |
| 長編の通読チェック | Gemini / Claude | 長いコンテキストを活かせる |
| Googleドキュメント連携 | Gemini | 標準連携 |
| 設定資料をファイルで管理しAIに参照させる | Claude Code / Cursor | エージェントがファイルを直接読む |

> 実務上は「1つに絞る」より「主力1つ＋セカンドオピニオン1つ」が効率的です。同じ原稿を別モデルに批評させると、片方が見落とした問題が見つかることがよくあります。

### 2-3. 小説特化ツール

#### Sudowrite

- **公式**: [sudowrite.com](https://sudowrite.com/)
- **主な機能**（公式ブログ「How Sudowrite Works」より）:
  - **Story Bible**: キャラクター、世界観、アウトラインを保持する設定集。シリーズ間で共有するSeries Folderもある
  - **Write**: 手が止まったところから続きを書く。直前の原稿（公式説明では最大2万語程度）とStory Bibleを読んでから生成する
  - **Rewrite / Describe / Brainstorm / Expand**: 書き直し、五感描写の追加、ブレスト、アウトラインから下書きへの展開
  - **Muse**: フィクション向けに訓練された独自モデル。公式は「ダークな場面も拒否しにくい」と説明
  - **Chat**: Story Bibleと原稿を見たうえでの相談（Chat onlyモードはクレジット非消費と説明）
- **料金**（2026年9月時点の公式ページ表示。年払い割引あり、**要確認**）: Hobby & Student 月10ドル（225,000クレジット）、Professional 月22ドル、Max 月44ドル（200万クレジット、繰越あり）。月払いではより高い価格表示の比較記事もある。
- **日本語**: 公式FAQでは多言語に対応しつつ、一部機能では英語にフォールバックすることがあると説明。日本語作品で使う場合は無料トライアルで確認推奨。
- **向いている人**: 英語で書く人、設定不要ですぐ使いたい人、描写を膨らませたい人。

#### Novelcrafter

- **公式**: [novelcrafter.com](https://www.novelcrafter.com/)
- **主な機能**: 
  - **Codex**: キャラ・場所・用語の辞書。本文中に登場すると自動でAIの文脈に入る
  - **シーンビート**: 「このシーンで起きること」を箇条書きし、そこから散文を生成
  - **BYOK（Bring Your Own Key）**: OpenAI、Anthropic、OpenRouter、ローカルモデル等、自分のAPIキーでモデルを選べる
  - チャット、レビュー機能、共同執筆（上位プラン）
- **料金**（公式価格ページ、地域により表示通貨が変わる。**要確認**）: Scribe 月4ドル（AIなし）、Hobbyist 月8ドル（BYOKでAI利用可）、Artisan 月14ドル（チャット等）、Specialist 月20ドル（共同執筆）。21日間の無料トライアル。AI利用料は各APIプロバイダに別途支払い。
- **向いている人**: シリーズ物を書く人、どのモデルに何を見せるかを細かく制御したい人、複数モデルを試したい人。

#### NovelAI

- **公式**: [novelai.net](https://novelai.net/)
- **特徴**: 補完型（文章の続きを予測して書く）ストーリー生成と、画像生成（NovelAI Diffusion）の二本柱。Lorebook（設定辞書）でキャラ・用語を管理できます。
- **2026年の動き**（公式ブログ・ジャーナルより）:
  - 2026年3月31日: テキスト生成新モデル「Xialong（シャーロン／夏龍）」をOpusプラン限定で提供開始。ZhipuAIのGLM-4.6をベースに独自データでファインチューンしたと説明
  - 2026年8月21日: 画像生成モデル「NovelAI Diffusion V5」公開。日本語プロンプトに公式対応
  - Opusプランでの画像生成V5に利用上限を導入するなど、サブスクの扱いが変更（詳細は要確認）
- **向いている人**: 雰囲気・文体重視で続きを書かせたい人、キャラクターのビジュアルも作りたい人。

#### AIのべりすと

- **公式**: [ai-novel.com](https://ai-novel.com/)（運営: Bit192 Labs）
- **特徴**: 日本語に最適化された国産の補完型小説AI。メモリ、脚注、キャラクターブックなどで設定を与えながら続きを書かせる方式です。無料プランと複数の有料プランがあります。
- **2026年の動き**（AI tellerのニュース記事による。**公式で要確認**）: 2026年春に500B〜1Tパラメータ級の「すぴこさまUltra-exp」を上位会員向けに稼働、5月28日に入門有料プラン向けの高速版「すぴこさま-04 ⚡️イナズマ」を追加したと報じられています。
- **向いている人**: 日本語ラノベ・Web小説調の文章を補完型で書きたい人。指示追従型（「〜を書いて」）ではなく、「書き出しを与えて続きを書かせる」使い方に慣れると強い。

| ローカルLLM（Ollama、LM Studio等） | 手元のPCでモデルを動かす | 未発表原稿を外部に出したくない場合の選択肢。性能はPC次第 |

### 2-4. 「指示追従型」と「補完型」の違い

小説特化ツールを選ぶ際に重要なのが、この区別です。

| 型 | 代表 | 使い方 | 長所 | 短所 |
| --- | --- | --- | --- | --- |
| 指示追従型 | Claude、ChatGPT、Gemini、Sudowriteの多くの機能 | 「〜について書いて」「この文を直して」 | 意図を伝えやすい、分析・批評ができる | 平均的・説明的な文になりやすい |
| 補完型 | AIのべりすと、NovelAI | 本文の途中まで書き、続きを生成させる | 文体・リズムを引き継ぎやすい、意外性がある | 細かい指示が効きにくい、話が逸れやすい |

**効率的な組み合わせ例**:
- プロットと批評は指示追従型、詰まったシーンの「別ルートの続き」探索は補完型。
- 補完型で出した続きは「アイデアの素材」として読み、本文は自分で書く（新人賞の補助的利用の範囲に収めやすい）。

## 第3章 執筆環境の構築: Claude Code / Cursor / MCP / Agent Skills

この章は本レポートの中核です。**「作品の全設定を知っているAI」を、ファイルとルールで作る**方法を説明します。プログラミング経験がなくても、フォルダとMarkdownファイルを作れれば始められます。

### 3-1. なぜ「リポジトリ化」なのか

チャット画面で長編を書いていると、次の問題が必ず起きます。

- 会話が長くなるとAIが序盤の設定を忘れる（コンテキストの圧縮・切り捨て）
- 新しいチャットを開くたびに設定を貼り直す手間
- 「どのバージョンの設定が正しいか」が分からなくなる
- AIが書き換えた箇所を追跡できない

これを解決するのが、**作品をフォルダ（できればGitリポジトリ）として管理し、AIエージェントにそのフォルダを作業場として与える**方式です。

| 観点 | チャットのみ | リポジトリ化 |
| --- | --- | --- |
| 設定の保持 | 会話依存で消える | ファイルとして永続 |
| 参照 | 毎回貼り付け | AIが必要なファイルを自分で読む |
| 変更履歴 | 追えない | Gitで差分・巻き戻しが可能 |
| 規約対応（記録保存） | スクショ頼み | プロンプトログと差分が自然に残る |
| 複数ツール | 移行が困難 | Markdownなのでどのツールでも読める |

### 3-2. 推奨フォルダ構成

```text
my-novel/
├── CLAUDE.md                 # Claude Code向けの作品ルール（最重要）
├── AGENTS.md                 # 他エージェント向け（内容はCLAUDE.mdと共通化してよい）
├── .cursor/
│   └── rules/
│       └── novel.mdc         # Cursor向けルール
├── .claude/
│   └── skills/
│       ├── proofread-ja/
│       │   └── SKILL.md      # 日本語校正スキル
│       └── continuity-check/
│           └── SKILL.md      # 設定矛盾チェックスキル
├── bible/                    # 設定資料（作品の聖典）
│   ├── 00_concept.md         # コンセプト・テーマ・ターゲット読者
│   ├── style_guide.md        # 文体ガイド・表記ルール・禁止表現
│   ├── glossary.md           # 用語集（固有名詞・読み・表記）
│   ├── timeline.md           # 年表・作中時系列
│   ├── characters/
│   │   ├── _template.md
│   │   ├── protagonist_aoi.md
│   │   └── rival_kaito.md
│   └── world/
│       ├── magic_system.md
│       └── places.md
├── plot/
│   ├── synopsis.md           # 全体あらすじ
│   ├── structure.md          # 三幕構成・ビートシート
│   ├── foreshadowing.md      # 伏線台帳（張った場所／回収予定）
│   └── chapters/
│       ├── ch01_outline.md
│       └── ch02_outline.md
├── manuscript/               # 本文
│   ├── ch01.md
│   └── ch02.md
├── summaries/                # 章ごとの要約（AIが参照する圧縮記憶）
│   ├── ch01_summary.md
│   └── ch02_summary.md
├── reviews/                  # AIの批評・校正結果
└── logs/
    └── ai_usage.md           # AI利用記録（新人賞・投稿サイト申告用）
```

**ポイント**:
- `summaries/` が長編の要です。本文全体を毎回読ませるとコストも時間もかかるので、各章を書き終えたら「500〜800字の要約＋この章で変化した設定」を作り、以後はそれを参照させます。
- `foreshadowing.md`（伏線台帳）は、AIに「回収漏れ」を検出させるのに非常に有効です。
- `logs/ai_usage.md` は、後述の新人賞・投稿サイトの申告に直接使えます。

### 3-3. キャラクターシートのテンプレート

```markdown
---
name: 篠宮 葵（しのみや あおい）
role: 主人公
age: 17
first_appearance: ch01
status: 生存
last_updated: ch05
---

# 篠宮 葵

## 一言で
嘘を見抜けるが、自分の嘘には気づけない少女。

## 外見
- 黒髪ショート、右耳にだけピアス穴
- 制服の上に兄のお下がりのカーディガン（袖が長い）

## 性格・価値観
- 表: 冷静、皮肉屋、面倒見がいい
- 裏: 見捨てられることへの恐怖
- 譲れないもの: 約束を破らないこと

## 口調
- 一人称: 「あたし」 / 二人称: 「あんた」（目上には「〇〇さん」）
- 語尾: 「〜じゃん」「〜でしょ」。敬語は苦手で崩れがち
- 口癖: 「はいはい」（照れ隠し）
- 絶対に言わないこと: 「わたくし」「〜ですわ」、長い説明台詞

## 台詞サンプル
- 「はいはい、分かったって。……で、本当は何があったの」
- 「嘘つくなら、もうちょっと上手くやりなよ」

## 能力・制約
- 他人の嘘は「声の温度」で分かる。文字・録音では不可
- 使いすぎると翌日まで味覚がなくなる

## 関係
- 篠宮 蒼（兄）: 3年前に失踪。葵は「捨てられた」と思っている
- 鳴海 海斗: 幼なじみ。葵は彼の嘘だけ見抜けない（理由は第3幕で判明）

## アーク（変化）
- 開始: 他人を信じない
- 中盤: 海斗に裏切られたと誤解する
- 終盤: 自分自身についていた嘘（兄を憎んでいる）を認める

## 章ごとの変化ログ
- ch03: 能力の副作用が初めて描写される
- ch05: 海斗に兄のことを話す（初めて）
```

> **AI向けのコツ**: 「口調」「絶対に言わないこと」「台詞サンプル」は、AIのキャラ崩壊防止に特に効きます。抽象的な性格描写より、具体的な台詞サンプル3〜5個のほうが再現性が高くなります。

### 3-4. CLAUDE.md の設定例

Claude Codeは作業フォルダ直下の `CLAUDE.md` を自動で読み込みます。作品の「憲法」として書きます。長すぎると肝心な指示が埋もれるため、**詳細は `bible/` に置き、CLAUDE.mdは目次と絶対ルールに絞る**のがコツです。

```markdown
# 作品: 『嘘の温度』（仮）

## このリポジトリについて
長編ライトミステリー（全12章・約12万字予定）の執筆リポジトリ。
あなたは「編集者兼校閲者」として作業する。本文の代筆は、明示的に指示されない限り行わない。

## 必ず最初に読むファイル
1. bible/00_concept.md（テーマ・読者層）
2. bible/style_guide.md（文体・表記ルール）
3. 作業対象の章の plot/chapters/chXX_outline.md
4. 直前2章分の summaries/

キャラクターが登場する場面を扱うときは bible/characters/ の該当ファイルを必ず読むこと。

## 絶対ルール
- 設定ファイルに書かれていない設定を勝手に追加しない。必要なら「提案」として別記する
- 視点は各章1人称（葵）で固定。他キャラの内心を地の文で書かない
- 固有名詞の表記は bible/glossary.md に従う
- 本文ファイル（manuscript/）を編集する前に、必ず変更案を提示して承認を得る
- 批評・校正の結果は reviews/ に `chXX_YYYYMMDD_種類.md` で保存する

## 文体の要点（詳細は style_guide.md）
- 短文と長文のリズムを交互に。1文60字を超えたら分割を検討
- 比喩は1段落に1つまで
- 禁止表現: 「〜のだった」の連続、「静寂が支配する」「時が止まったかのような」、感情の直接説明（「悲しかった」等）の多用

## 作業後に必ずやること
- 章を書き終えたら summaries/chXX_summary.md を作成（600字以内＋設定変更点の箇条書き）
- 新しい伏線は plot/foreshadowing.md に追記
- キャラの状態変化は該当キャラシートの「章ごとの変化ログ」に追記
- logs/ai_usage.md に今回のAI利用内容を1行で追記
```

### 3-5. Cursor のルール設定例

Cursorでは `.cursor/rules/` に `.mdc` ファイルを置くとエージェントへの指示として使われます（ルールの形式や適用条件の指定方法はバージョンで変わることがあるため要確認）。`AGENTS.md` を読む機能もあるため、共通の内容を `AGENTS.md` に置き、ツール固有の差分だけ各ルールに書くと管理が楽です。

```markdown
---
description: 小説原稿の編集・校正ルール
globs: ["manuscript/**/*.md", "plot/**/*.md"]
alwaysApply: false
---

# 小説執筆ルール

- このプロジェクトは日本語の長編小説である。コードではなく文章を扱う
- 原稿を編集する際は bible/style_guide.md と bible/glossary.md を参照する
- 編集はできるだけ小さな単位で提案し、意図を1行で説明する
- 台詞を修正するときは bible/characters/ の口調設定と台詞サンプルに合わせる
- 地の文の視点人物は章冒頭の front matter `pov:` に従う
- 「より良くする」系の曖昧な全面書き換えは禁止。指摘→提案→承認の順で進める
```

**Cursorを執筆に使うときの小技**:
- Markdownプレビューを横に開き、縦書き風プレビュー拡張を入れると読みやすい（拡張機能は各自確認）
- `@ファイル名` で設定資料を明示的に文脈へ追加できる
- 差分表示でAIの修正を1行ずつ採用・却下できる。これが推敲で非常に強力
- Gitの差分がそのまま「AIがどこを直したか」の記録になる

### 3-6. Agent Skills（SKILL.md）の作り方

**Agent Skills** は、指示・メタデータ・必要に応じてスクリプトやテンプレートをフォルダにまとめたものです。Anthropicの公式ドキュメントによると、各スキルには YAML フロントマター（`name` と `description`）付きの `SKILL.md` が必須で、Claudeはリクエストが `description` に合致したときに初めて本文を読み込みます。つまり、**普段はコンテキストを消費せず、必要なときだけ手順書が開かれる**仕組みです。

- 個人用: `~/.claude/skills/<スキル名>/SKILL.md`
- プロジェクト用: `<リポジトリ>/.claude/skills/<スキル名>/SKILL.md`
- claude.ai の設定画面やAPI（Skills API）からもアップロード可能（詳細は公式ドキュメントで要確認）
- 形式はオープンな仕様として公開されており、Cursor、Codex CLI、OpenCodeなど他のエージェントでも同じ `SKILL.md` を使える場合がある（対応状況は各ツールで要確認）

#### スキル例1: 日本語校正スキル

```markdown
---
name: proofread-ja
description: 日本語小説原稿の校正を行う。誤字脱字、表記揺れ、ら抜き言葉、二重敬語、句読点、三点リーダー・ダッシュの表記、用語集との不一致を検出する。ユーザーが「校正」「誤字チェック」「表記揺れ」と言ったときに使う。
---

# 日本語小説校正の手順

1. bible/glossary.md と bible/style_guide.md を読む
2. 対象ファイルを読み、以下を検出する
   - 誤字脱字・変換ミス（例: 以外/意外、関心/感心）
   - 表記揺れ（例: 「出来る/できる」「言う/いう」）→ style_guide の方針に合わせる
   - 三点リーダーは「……」（2個）、ダッシュは「――」（2個）
   - 感嘆符・疑問符の後は全角スペース（文末の閉じ括弧前を除く）
   - 用語集と異なる固有名詞
3. 文体や内容の改善提案はしない（校正の範囲に限定する）
4. 結果を以下の表形式で reviews/ に保存する

| 行 | 原文 | 修正案 | 種別 | 確信度 |
|---|---|---|---|---|

5. 確信度が低いものは「要著者判断」と明記する
```

#### スキル例2: 設定矛盾チェックスキル

```markdown
---
name: continuity-check
description: 小説の設定矛盾・時系列矛盾・キャラクター口調のブレ・伏線の回収漏れを検出する。「矛盾チェック」「整合性」「継続性」「伏線確認」と言われたときに使う。
---

# 継続性チェック手順

## 入力
- 対象章: manuscript/chXX.md
- 参照: bible/characters/*, bible/timeline.md, plot/foreshadowing.md, summaries/*

## 手順
1. 対象章に登場する人物・場所・アイテムを列挙する
2. 各人物について、キャラシートの「口調」「絶対に言わないこと」と台詞を照合する
3. 時間表現（曜日、季節、経過日数、時刻）を timeline.md と照合する
4. 前章までの summaries と矛盾する事実（怪我、所持品、知っている情報）を探す
5. foreshadowing.md の「回収予定: chXX」の伏線が扱われているか確認する

## 出力形式
### 矛盾（確実）
- [場所] 内容 / 根拠ファイルと該当箇所
### 疑わしい点（要確認）
- ...
### 伏線の状況
- 回収済み / 未回収 / 新規に張られた可能性があるもの

## 禁止
- 修正を本文に直接書き込まない
- 設定ファイルにない「正解」を推測で作らない
```

#### スキル例3: 章要約スキル

```markdown
---
name: chapter-summary
description: 書き上がった章から、後続の執筆でAIが参照するための要約と設定変更ログを作る。「要約」「章まとめ」「サマリー作成」のときに使う。
---

# 章要約の作り方
1. manuscript/chXX.md を通読する
2. summaries/chXX_summary.md を以下の形式で作成する

   - この章で読者が新たに知った情報
   - 登場人物の状態変化（怪我・感情・関係・所持品）
   - 張られた伏線／回収された伏線

3. キャラシートの「章ごとの変化ログ」と foreshadowing.md への追記案を提示する（直接編集は承認後）
```

### 3-7. MCPサーバーの活用

**MCP（Model Context Protocol）** は、AIアプリと外部のツール・データをつなぐ標準プロトコルです。スキルが「手順の知識」なのに対し、MCPは「新しい道具とデータへの接続」を提供します。両者は補完関係にあります。

#### 執筆に役立つMCPサーバー

| MCPサーバー | 用途 | 備考 |
| --- | --- | --- |
| Filesystem（公式リファレンス実装） | 指定フォルダのファイル読み書き | Claude Desktopなど、ファイル操作機能がないクライアントで設定資料フォルダを読ませる。許可するフォルダは最小限に |
| Notion（公式: `@notionhq/notion-mcp-server` など） | Notionの設定資料データベースを検索・読み書き | Notionでキャラ・プロットを管理している人向け。公式のリモートMCPもある（要確認） |
| Obsidian系 | Vault内のノートを検索・読み書き | `mcp-obsidian`（Obsidianの Local REST API プラグインが必要）、`mcpvault`（ファイルを直接読む方式）など。比較記事あり。いずれも第三者製で要確認 |
| Memory（公式リファレンス実装のナレッジグラフ型） | エンティティと関係を記憶 | キャラ相関の記憶に使えるが、作品設定はファイルで持つほうが管理しやすい |
| Git | 履歴・差分の参照 | Claude Code / Cursorは標準でGitを扱えるため、多くの場合不要 |
| Web検索・Fetch系 | 時代考証や資料の下調べ | 事実は必ず一次資料で確認 |
| Google Drive / Docs系 | Googleドキュメント原稿へのアクセス | 公式・非公式が複数あり要確認 |

> MCPサーバーの名称・パッケージ名・インストール方法は変化が速いため、導入時は各リポジトリのREADMEと [modelcontextprotocol.io](https://modelcontextprotocol.io/) の情報を要確認としてください。

#### 設定例（Claude Code のプロジェクト用 `.mcp.json`）

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
```

## 第4章 具体的なワークフロー（構想→プロット→執筆→推敲→校正→投稿）

### 4-0. 全体像

| 段階 | AIの役割 | 人間の役割 | 成果物 | 時短効果 |
| --- | --- | --- | --- | --- |
| ①構想 | 発散、問いかけ、類似作の傾向整理 | 「書きたいもの」の決定 | `00_concept.md` | 大 |
| ②プロット | 構成案の比較、穴の指摘、ビート分解 | 構成の採択、山場の設計 | `synopsis.md` `structure.md` 章アウトライン | 大 |
| ③執筆 | シーンの選択肢提示、詰まり解消、描写素材 | 本文を書く（規約に応じて） | `manuscript/chXX.md` | 中 |
| ④推敲 | 批評、読者視点の感想、冗長箇所の指摘 | 修正の判断と書き直し | `reviews/` 修正版 | 大 |
| ⑤校正 | 誤字脱字、表記揺れ、用語集照合 | 最終確認 | 校正済み原稿 | 特大 |
| ⑥投稿 | あらすじ・タイトル・タグ案、申告文の下書き | 規約確認と申告、公開判断 | 投稿ページ | 中 |

### 4-1. ①構想: 「書きたい核」を言語化する

構想段階でAIに「面白い話を考えて」と頼むと、どこかで見たような平均的なアイデアが返ってきます。効率的なのは逆で、**AIに質問させて自分の中の核を引き出す**方法です。

**手順**:
1. 自分のメモ（好きな作品、書きたいシーン、テーマの断片）を雑多なまま渡す
2. AIにインタビューさせる（1問ずつ、10問程度）
3. 回答からコンセプト文（一文ログライン）を3案作らせる
4. 人間が1つ選び、`00_concept.md` に確定させる
5. 「このコンセプトで陳腐になりやすい点」をAIに挙げさせ、差別化ポイントを決める

**00_concept.md の項目例**:
- ログライン（1文）
- テーマ（作品が問いかけること）
- ジャンルとサブジャンル、想定文字数
- ターゲット読者（年齢層、好きそうな既存作のタイプ）
- 読後感（読者に残したい感情）
- 「この作品だけの売り」3つ
- 避けたい展開・表現

### 4-2. ②プロット: 構成案を比較して選ぶ

プロット段階はAIが最も時短に貢献する工程の一つです。ポイントは**1案を作らせるのではなく、複数案を比較させる**ことです。

**手順**:
1. コンセプトから三幕構成（または起承転結、Save the Catのビートシート等）で3案作らせる
2. 各案の長所・短所・読者の離脱リスクを表で比較させる
3. 人間が1案を選ぶか、案を組み合わせる
4. 章ごとのアウトラインに分解（各章: 目的、起きること、感情の変化、引き）
5. 伏線台帳を作る（張る章・回収する章）
6. AIに「辛口編集者」として穴を指摘させる → 修正

**章アウトラインのテンプレート**:

```markdown
---
chapter: 3
pov: 葵
target_length: 8000
---
# 第3章「温度のない声」

## この章の目的
葵の能力の副作用を初めて見せ、代償があることを読者に印象づける

## 起きること（シーン単位）
1. 放課後の図書室。海斗が嘘をつくが、葵には分からない
2. 帰り道、能力を使いすぎて味覚が消える（初描写）
3. 夕食。母に気づかれまいと平静を装う

## 感情の流れ
苛立ち → 不安 → 孤独

## 伏線
- 張る: 海斗の嘘だけ見抜けない（理由は第10章で回収）
- 回収: なし

## 章末の引き
兄からの古いメッセージが届く
```

### 4-3. ③執筆: 規約に合わせて「AIの関与度」を選ぶ

執筆段階では、作品の発表先によってAIの使い方を変える必要があります（詳細は第7章）。

| 関与レベル | 内容 | 新人賞（補助的利用のみの賞） | カクヨム推奨タグ | なろう区分（目安） |
| --- | --- | --- | --- | --- |
| L0 | AI不使用 | 可 | なし | AI不使用 |
| L1 | アイデア出し・資料調査・校正のみ | 多くの賞で可（申告必要） | AI補助利用 | AI補助的利用 |
| L2 | AIの下書きや素材を参考に、作者が全面的に自分の表現で書く | 賞によっては不可・要確認 | AI補助利用〜AI本文一部利用（実態で判断） | AI間接利用 |
| L3 | AI生成文の一部を本文にそのまま（または軽微修正で）使う | 多くの賞で不可 | AI本文一部利用（50%未満目安） | AI直接使用 |
| L4 | 本文の大半がAI生成 | 不可（星新一賞等一部を除く） | AI本文利用 | AI直接使用（全編AI生成は禁止事項） |

※区分の当てはめはあくまで本レポートの目安です。最終判断は各サイト・各賞のガイドラインに照らして作者が行う必要があります。

#### L1（補助）での執筆テクニック

- **詰まり解消の質問**: 「このシーンで葵が取り得る行動を5つ、意外性の高い順に。本文は書かないで」
- **描写の素材集め**: 「11月の夕方の図書室で感じ得る五感の要素を列挙して」（素材リストを見て自分で書く）
- **台詞のチェック**: 自分で書いた台詞を見せて「キャラシートの口調と比べてズレている箇所」を指摘させる
- **シーンの目的確認**: 書く前に「このシーンが物語上果たす役割」をAIと確認する

#### L2〜L3（下書き活用）でのテクニック（規約が許す場合）

- シーンビート（箇条書き）からAIに複数バージョンの下書きを作らせ、良い要素だけ拾って自分で書き直す
- 補完型AI（AIのべりすと等）に冒頭数行を与えて分岐を複数出し、展開のヒントにする
- 文体ガイドと自分の過去原稿サンプルを与え、「骨組み」だけ生成させる

**どのレベルでも共通**: 生成物とプロンプトを `logs/` に残す。後から申告・説明を求められても対応できます。

### 4-4. ④推敲: 「批評させて自分で直す」

推敲は、AIを**複数の視点を持つ読者**として使うと効果的です。

**推敲の3パス**:
1. **構造パス**（章単位）: シーンの順序、ペース、目的が果たされているか、引きは効いているか
2. **キャラ・継続性パス**: 口調、動機の一貫性、設定矛盾（`continuity-check` スキル）
3. **文章パス**（段落単位）: 冗長、説明過多、比喩の過剰、リズム、語尾の単調さ

**ペルソナ別批評**:
- 辛口の担当編集者
- ジャンルを読み慣れた熱心な読者
- 初めてこのジャンルを読む読者
- 3話で切る判断をするWeb小説読者

> **重要**: AIの指摘を全部採用すると、作品が「無難」になります。指摘は「気づきのリスト」として扱い、採否は自分で決めてください。複数のペルソナが同じ箇所を指摘したら、そこは本当に問題がある可能性が高い、という使い方が有効です。

### 4-5. ⑤校正: 機械的チェックはAIに任せる

校正は最もAIに任せやすい工程です。ただし**誤検出（正しいものを誤りとする）**もあるため、表形式で出させて一つずつ判断するのが安全です。

**チェック項目**:
- 誤字脱字、変換ミス、同音異義語
- 表記揺れ（漢字／ひらがな、送り仮名）
- 用語集との不一致（固有名詞、呼称）
- 記号の作法（……、――、！？の後の全角スペース、括弧内の句点）
- ら抜き・さ入れ・い抜き（台詞では意図的な場合あり）
- 二重表現（「まず最初に」「頭痛が痛い」）
- 同じ語尾の連続、同じ単語の近接反復

**運用のコツ**: Gitを使っていれば、AIに直接修正させた後に差分を見て一つずつ確認する方式も効率的です。ただし新人賞の規定によっては「表現の整え」までが補助的範囲とされるため、内容に踏み込む修正は避けましょう。

### 4-6. ⑥投稿: あらすじ・タイトル・タグ・申告

- **タイトル案**: ジャンルの慣習（Web小説の長文タイトル等）を踏まえて20案 → 自分で選ぶ・組み合わせる
- **あらすじ**: 200字版・400字版・キャッチコピー（35字以内など各サイトの制限に合わせて要確認）
- **タグ案**: ジャンル・要素タグ。**AI利用タグ・区分は必ず自分で規約を読んで判断**
- **申告文**: 新人賞の備考欄用に「利用ツールと目的」を簡潔にまとめた文を下書き（`logs/ai_usage.md` から作成）
- **更新スケジュール**: 連載なら予約投稿計画。なろうではAI利用状況未設定だと予約掲載に制限がある点に注意

### 4-7. 連載作家向け: 1話（3,000〜5,000字）の時短ループ

```text
[前日・15分] 次話アウトライン作成（AIと壁打ち）→ plot/chapters/
[当日・60〜90分] 本文執筆（自分で）
[当日・10分] AIで批評（構造＋キャラ）→ reviews/
[当日・20分] 修正
[当日・5分] AIで校正 → 確認して反映
[当日・5分] 要約作成（chapter-summary スキル）→ summaries/
[当日・5分] 投稿・ai_usage.md に記録・git commit
```

### 4-8. 長編（10万字以上）向け: マイルストーン管理

| マイルストーン | AIでやること |
| --- | --- |
| 25%地点 | 第一幕の通読チェック（キャラ紹介の過不足、フックの強さ） |
| 50%地点 | ミッドポイントの効果、中だるみ検出、伏線台帳の棚卸し |
| 75%地点 | クライマックスへの準備状況、未回収伏線リスト |
| 完成時 | 全体通読（長文コンテキストのモデルで）、矛盾の総点検、あらすじ作成 |

## 第5章 プロンプト集

プロンプトはそのままコピーして使えるように書いています。`{ }` の部分を置き換えてください。共通のコツは、**役割・入力・制約・出力形式を明示すること**、そして**「本文を書かないで」など、やってほしくないことも書くこと**です。

### 5-1. 構想

**P01: インタビューで核を引き出す**

```text
あなたは新人作家の構想を引き出す経験豊富な編集者です。
以下は私の雑多なメモです。これを読んだうえで、私が本当に書きたいものを
明らかにするための質問を、1回に1問ずつ、合計10問してください。
私の回答を聞いてから次の質問をしてください。アイデアの提案はまだしないでください。

# メモ
{好きな作品、書きたいシーン、テーマの断片などを箇条書きで}
```

**P02: ログライン3案**

```text
これまでの質疑応答を踏まえて、作品のログライン（1文のあらすじ）を3案作ってください。
各案について「主人公」「欲求」「障害」「賭け金（失敗したら何を失うか）」を分解し、
最後に3案の違いを1行ずつで説明してください。
```

**P03: 陳腐化チェック**

```text
以下のコンセプトは、同ジャンルでありがちな展開に陥る危険がどこにありますか。
「ありがちな展開」を5つ挙げ、それぞれに対して、このコンセプトならではの
ひねり方を2つずつ提案してください。具体的な既存作品名は挙げなくて構いません。

# コンセプト
{00_concept.md の内容}
```

**P04: 「もしも」展開**

```text
次の設定について「もしも〜だったら」という仮定を15個出してください。
物語の根幹を揺るがすもの5個、キャラクター関係を変えるもの5個、
世界観の細部に関わるもの5個に分けてください。

# 設定
{世界観やキャラクターの概要}
```

**P05: ターゲット読者の解像度を上げる**

```text
この作品のターゲット読者像を3パターン描写してください。
それぞれ「年齢・生活」「普段読む作品の傾向」「この作品に期待すること」
「がっかりするポイント」を書いてください。
```

### 5-2. キャラクター・世界観

```text
{キャラシート}
```

**P07: 台詞サンプル生成（口調の確定用）**

```text
- 怒っているとき / 照れているとき / 嘘をつくとき / 目上の人と話すとき / 独り言
これは本文には使わず、口調の確認用です。設定と矛盾する点があれば併記してください。

{キャラシート}
```

**P08: キャラの動機の一貫性チェック**

```text
{…}
```

**P09: 世界観のルール検証**

```text
{世界観設定}
```

**P10: 用語集の作成**

**P16: 中だるみ検出**


### 5-4. 執筆（補助的利用）

**P17: 次の行動の選択肢**

## 第7章 投稿サイトの規約・新人賞のAI規定・著作権

> **最重要の注意**: この章の内容は2026年9〜10月時点で確認できた情報の要約です。規約・要項は改定されます。**投稿・応募の前に、必ず各サイト・各賞の最新の原文を確認してください。** 本章は法的助言ではありません。

### 7-1. カクヨム

- **2026年5月27日**: 小説投稿ガイドラインを更新し、生成AIを使用した作品へのタグ付けを推奨すると明記。
- **タグ区分**（ガイドラインより要約）:

| 使用状況 | タグ |
| --- | --- |
| 本文の大半（目安50%以上）が生成AIで生成された文章、またはそれに作者が軽微な修正を加えたもの | AI本文利用 |
| 本文の一部（目安50%未満）が生成AIで生成された文章、またはそれに作者が軽微な修正を加えたもの | AI本文一部利用 |
| 生成AIのアイデアや資料をもとに作者自身が本文を書いたもの、または作者自身が書いた文章の校正を生成AIに行わせるなど、創作の補助的に利用したもの | AI補助利用 |

- **補足**: 検索サービスなど日常で使うツールのAI補助機能や、ドキュメントソフトの自動校正機能は「AI補助利用」に該当しないと説明されています。2025年11月の追記では、「作者が意識的に生成AIツールを利用した場合」の適用を想定していると説明。
- **コンテストでは必須**: 「カクヨムコンテスト11」の注意事項や、「カクヨムときめく小説大賞【ナツガタリ'26】」の応募要項では、タグ付けが必須とされ、タグと実際の利用状況が異なる場合は選考対象外となると記載されています。タグがあることでランキング等で不利になることはないとも説明されています。

### 7-5. 著作権の基本（文化庁「AIと著作権に関する考え方について」より）

文化審議会著作権分科会法制度小委員会が2024年3月に取りまとめた「AIと著作権に関する考え方について」と、その後の解説資料・セミナー資料の要点を、小説執筆の観点で整理します。

#### (1) AI生成物は著作物になるか

- **AIが自律的に生成したものは著作物に該当しない**（「思想又は感情を創作的に表現したもの」ではないため）。
- **人がAIを「道具」として使った場合は著作物になり得る**。判断基準は、人の**創作意図**と**創作的寄与**。
- 創作的寄与の判断で考慮される要素:
  - **指示・入力の分量と内容**: 創作的表現といえるものを具体的に示す詳細な指示は、寄与ありと評価される可能性を高める。一方、長大なプロンプトでもアイデアを示すにとどまるなら寄与とは言いにくい
  - **生成の試行回数**: 単に回数が多いだけでは寄与にならないが、生成結果を確認して指示を修正しながら試行を重ねる場合は考慮され得る
  - **複数の生成物からの選択**: 他の要素と組み合わせて考慮され得る
- **人間が創作的表現といえる加筆・修正を加えた部分は、通常、その部分に著作物性が認められる**。
- 判断は個別具体的な事情に応じて行われ、「AI生成物だから一律に著作物でない」とはならない。

**小説執筆への含意**: 本文を自分で書く（L0〜L2）限り、通常の著作物として扱われる可能性が高い。AI生成文をそのまま使う（L3〜L4）部分は、著作物性が認められない可能性があり、権利主張や商業化で不利になり得る。MF文庫J新人賞の「著作権を法的に認めることが困難な生成AIの利用と判断した場合は審査対象外」という規定はこの点を踏まえたものと読めます。

#### (2) 既存作品の権利侵害にならないか

- 「AI生成物が著作物になるか」と「AI生成物の生成・利用が既存著作物の侵害になるか」は**別の問題**。
- 侵害の判断は、通常の著作権侵害と同じく**類似性**と**依拠性**。
- AIで既存作品と類似したものが生成された場合、依拠性が推認され得るとの考え方が示されている。
- **作風・画風そのものはアイデアとして保護されない**が、特定作家の作品群の創作的表現が直接感得できるような生成物は侵害に当たり得る。

**小説執筆での実務的な注意**:
- 「〇〇（実在作家）の文体で」「〇〇（既存作品）の続きを」といったプロンプトで生成した文を使うのは避ける
- 既存作品の本文を大量にAIに読ませて模倣させない
- 二次創作は、AI利用以前に原作者・投稿サイトのガイドラインに従う
- 星新一賞の要項にあるように、応募前にインターネット検索等で既存作品と酷似していないか確認する

#### (3) ツールの利用規約

- 生成物の権利帰属や商用利用の可否は、**各AIサービスの利用規約**で定められます。多くの主要サービスは出力の権利を利用者に帰属させる趣旨の条項を置いていますが、無料プランと有料プランで扱いが異なるサービスもあり、要確認です。
- 星新一賞のように「ツールの規約がコンテスト応募・出版・映像化・翻訳などを禁止していれば応募不可」と明記する賞もあります。

## 第8章 落とし穴と品質を上げるコツ

### 8-1. よくある落とし穴

| 落とし穴 | 症状 | 原因 | 対策 |
| --- | --- | --- | --- |
| 文章の均質化 | どの場面も同じテンションで、整っているが印象に残らない | AIは「平均的にもっともらしい」文を出しやすい | 本文は自分で書く。AIには批評させる。自分の文体ガイドを作る |
| AI特有の定型表現 | 「静寂が支配した」「胸の奥で何かが」「〜のだった。」の連続、三点列挙の多用 | 学習データ由来の癖 | 禁止表現リストを `style_guide.md` に。P28で検出 |
| 設定の静かな崩壊 | 3章前に死んだはずの人物が会話に参加、呼称が変わる | 会話が長くなり序盤を参照できていない | 設定資料のファイル化、章要約、継続性チェック |
| キャラの「いい人化」 | 皮肉屋のキャラが素直に謝る、悪役が説明的に動機を語る | AIは対立や悪意を和らげがち | キャラシートに「絶対に言わないこと」と台詞サンプル |
| 説明過多 | 感情や状況をすべて地の文で説明する | 指示追従型AIは「分かりやすさ」を優先 | 「見せる」書き方を指示、P26で検出 |
| 指摘の全面採用 | 推敲するほど作品が無難になる | AIの批評は「欠点の除去」に偏る | 採否は自分で。複数ペルソナが一致した点だけ優先 |
| 事実誤認（ハルシネーション） | 架空の歴史的事実、存在しない法律・医療手順 | AIはもっともらしい誤りを出す | 事実はAIに断定させず、一次資料で確認（P33） |
| 規約違反・申告漏れ | 補助的利用のみの賞にAI下書きを使った原稿を応募 | 規約を読んでいない／範囲の誤解 | 応募先を先に決め、関与レベルを最初に設定（4-3） |
| 記録がない | 主催者から制作過程の開示を求められて答えられない | ログを残していない | Git＋`logs/ai_usage.md` を最初から |
| 依存と筆力低下 | AIなしで書けなくなる、自分の声が分からなくなる | 下書き生成への過度な依存 | 「1日○字は完全に自力で書く」などのルール |
| コストの膨張 | API料金やクレジットが想定以上 | 毎回全文を読ませる | 要約参照、モデルの使い分け、上限設定 |
| 未発表原稿の扱い | 学習利用や漏えいへの不安 | データ設定の確認不足 | 学習オプトアウト設定、ローカルLLM、プライベートリポジトリ |
| 他作品への接近 | 既存作品に似た展開・表現 | 「〇〇風に」というプロンプト | 実在作家・作品名を使った模倣指示をしない。応募前に類似チェック |

### 8-2. 品質を上げるコツ

#### コツ1: 「良い例」より「自分の例」を見せる

AIに文体を合わせさせたいときは、抽象的な説明（「透明感のある文体で」）より、**自分が書いた原稿の抜粋**を見せるほうが効果的です。P23で自分の文体を分析させ、`style_guide.md` を作っておきましょう。

#### コツ2: 制約を具体的にする

- 悪い例: 「もっと面白くして」
- 良い例: 「この場面の緊張感が途切れる原因を、台詞の長さと地の文の説明量の観点から3つ指摘して」

#### コツ3: 出力形式を指定する

表、箇条書き、引用付きなど、**後で判断しやすい形式**で出させると、推敲・校正の時間が大きく減ります。特に校正は「行 / 原文 / 修正案 / 種別 / 確信度」の表が便利です。

#### コツ4: 一度に頼む範囲を小さくする

「全体を良くして」より「第3章のシーン2の会話部分だけ、口調チェック」のほうが精度が高くなります。長編はシーン単位で回すのが基本です。

#### コツ5: 複数モデルでクロスチェック

同じ原稿をClaudeとGemini（またはChatGPT）に別々に批評させ、**両方が指摘した点**を優先して直します。モデルごとの癖が相殺されます。

#### コツ6: 「否定から入る」役を与える

AIは既定で肯定的なフィードバックをしがちです。「辛口編集者」「出版会議で反対する立場」「3話で切る読者」など、批判的な役割を明示すると有用な指摘が増えます。

#### コツ7: 要約をこまめに更新する

長編では、章要約とキャラシートの「変化ログ」を更新し続けることが、矛盾防止の最も確実な方法です。更新はAIに下書きさせ、人間が確認する運用で手間を減らせます。

#### コツ8: 人間が書く場所を決めておく

効率化を突き詰めても、**冒頭の一文、山場の台詞、ラストシーン**は自分で書く、と決めておくと、作品の「声」が守られます。読者の記憶に残るのはこうした箇所です。

#### コツ9: 音読とAIの併用

AIは文字列としての正しさは判定できても、**リズムや息継ぎ**は苦手です。最終稿は音読するか、読み上げ機能で聞いて確認しましょう。

#### コツ10: Gitで「怖くない推敲」を

AIに大胆な修正案を出させても、Gitがあればいつでも戻せます。ブランチを切って「大胆に削った版」と「元の版」を比較する、といった実験が気軽にできます。

### 8-3. 文体ガイド（style_guide.md）の例

```markdown
# 文体ガイド

## 基本
- 一人称（あたし）視点、過去形基調。緊迫場面のみ現在形を混ぜてよい
- 1文は平均30〜40字。60字を超える文は1段落に1つまで
- 段落は3〜5文。会話の前後で段落を切る

## 表記
- 可能の「できる」はひらがな
- 「〜という」はひらがな、「言う」は発話のみ
- 三点リーダー「……」、ダッシュ「――」
- 数字は漢数字（時刻・日付も）

## 禁止・抑制
- 「〜のだった」は1章に3回まで
- 「静寂が支配する」「時が止まったかのよう」「胸の奥で何かが」は使わない
- 感情語（悲しい、嬉しい、怖い）を地の文で直接書くのは1シーン1回まで
- 「まるで〜のように」の比喩は1段落に1つまで

## 好む表現
- 感情は身体感覚と行動で示す（例: 怒り→指先が冷える、袖を握る）
- 葵の皮肉は短く、語尾を切る
```

- [ ] 自分の利用が規定の範囲内か確認した（曖昧な点は主催者に問い合わせ）
- [ ] カクヨムならタグ（AI本文利用／AI本文一部利用／AI補助利用）を実態どおりに付けた（コンテストは必須）
- [ ] なろうならAI利用状況（不使用／補助的利用／間接利用／直接使用）を設定した
- [ ] 新人賞なら備考欄等に利用ツールと目的を記載した
- [ ] プロンプト・生成物・修正履歴を提示できる状態で保存している
- [ ] 既存作品との類似をチェックした（印象的なフレーズの検索など）
- [ ] 事実に依存する記述を一次資料で確認した
- [ ] 使用したAIツールの規約で、公開・出版・応募が禁止されていないことを確認した
- [ ] 差別的・誹謗中傷的な表現が意図せず含まれていないか自分の目で確認した

### 9-4. 品質チェック（推敲の最終段階）

- [ ] 冒頭3行で「何が問題か」「誰の話か」が伝わる
- [ ] 各シーンに目的がある（なくても成立するシーンはないか）
- [ ] 視点ブレがない
- [ ] キャラの口調がキャラシートと一致している
- [ ] 説明過多の箇所を削った
- [ ] AI的な定型表現が残っていない
- [ ] 章末に引きがある
- [ ] 伏線台帳の「今章回収」が回収されている
- [ ] 音読して引っかかる箇所がない
- [ ] 冒頭の一文・山場の台詞・ラストは自分の言葉で書いた

### 9-5. 環境構築チェック（中級者向け）

- [ ] Claude Code または Cursor を作品フォルダで起動できる
- [ ] `CLAUDE.md` / `AGENTS.md` / `.cursor/rules/` が機能している（AIが設定を参照しているか質問して確認）
- [ ] `.claude/skills/` に校正・継続性チェック・要約のスキルを置いた
- [ ] 必要に応じてObsidian／NotionのMCPを接続した（トークンはコミットしない）
- [ ] サービスのデータ利用設定（学習オプトアウト等）を確認した
- [ ] API利用の上限額を設定した
- [ ] リモートのプライベートリポジトリにバックアップしている
